# Deploying Walking Meditation to the client's new AWS account

Last reviewed against this repository: 12 November 2026

This is the authoritative, from-zero deployment procedure for the
`meditation-server` repository. The client creates and owns a new AWS account,
builds from a reviewed repository commit, and creates every AWS resource in that
account. This guide covers the AWS Console settings that CDK does not own, the
one-time account/bootstrap work, Aurora initialization, GitHub OIDC, environment
deployment, verification, and client acceptance. The workload is deliberately
restricted to `ap-southeast-2` (Asia Pacific, Sydney).

The project testing account is not handed over and is expected to become
defunct. Treat its deployments as historical test evidence only. Do not reuse or
migrate its account ID, IAM/OIDC roles, bootstrap resources, ARNs, Aurora
cluster, snapshots, application data, secrets, provider keys, SES identities,
buckets, API URLs, CloudFormation outputs, alarms, or logs. The source repository
is the only deployment artifact carried forward. Decommissioning the old testing
account is a separate responsibility for its owner and is not part of the
client's deployment procedure.

Do not process real participant data during setup. Use synthetic data until the
production launch gates in the operations handbook are approved. Never deploy a
dirty worktree, paste secret values into GitHub variables/CDK context, or use
CDK `--hotswap`, `--hotswap-fallback`, or `--express` for production.

## 1. Architecture and ownership boundary

CDK creates seven stacks:

- `WmIdentity` — GitHub OIDC provider/deployment roles;
- `WmAlerting-<stage>` — SNS and budget/operational alerting;
- `WmData-<stage>` — the application database credential secret;
- `WmGeneration-<stage>` — generation queue, worker, maintenance and dev archive;
- `WmExports-<stage>` — export queue, worker, maintenance and private bucket;
- `WmApi-<stage>` — FastAPI Lambda, REST API, logs, alarms, secrets, optional
  Polly permission, and production WAF; and
- `WmOperations-<stage>` — CloudTrail and audit resources.

Aurora PostgreSQL is an external prerequisite because this project uses Aurora
Express Configuration, which the repository provisions with the AWS CLI rather
than CloudFormation. Express creates an Aurora PostgreSQL Serverless cluster
that AWS describes as ready in seconds, through an AWS-managed Internet Access
Gateway and without a customer VPC. It is
IAM-only—there is no master password—and the administrator connects with a
short-lived token generated by `aws rds generate-db-auth-token`. AWS documents
the flow at <https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/CHAP_GettingStartedAurora.AuroraPostgreSQL.ExpressConfig.html>.

The application does not connect to the cluster endpoint. Lambda uses the RDS
Data API and a CDK-managed `wm_app` credential in Secrets Manager.

## 2. Prepare the client-owned source and account decisions

The client must place the reviewed source in a client-controlled GitHub
repository before configuring OIDC. Clone, mirror, or otherwise reproduce the
repository history according to the agreed delivery process; do not depend on
continued access to the project team's testing account or working copy.

Before the first client-account synthesis:

1. Set `context.githubRepository` in `cdk.json` to the exact client GitHub
   `<owner>/<repository>` value used in the OIDC subject claim. The repository's
   existing value is testing-repository-specific and must not be reused.
2. After installing dependencies in Section 4, but before the first synthesis,
   clear account-specific CDK lookup data left by the testing account:

   ```powershell
   npx cdk context --clear
   ```

3. Confirm `cdk.context.json` contains no testing-account ID. After synthesis in
   the client account, review and commit only the new client-account context.
4. Confirm generated `cdk.out` content and any local `.env` files are not treated
   as delivery inputs.

Record these in the approved client deployment/change record, not in source:

- new client AWS account ID, client root owner, and maintained billing, security
  and operations contacts;
- GitHub repository owner/name and production reviewers;
- environment(s): `dev` and, after production approval, `prod`;
- named budget and operational alert mailboxes;
- approved monthly budget and Lambda concurrency limits;
- SES sending domain/address and DNS ownership;
- Google Maps and OpenAI project owners and secret ARNs;
- whether TTS is `polly` or `disabled`;
- production WAF rollout state (`count` first, then `block`);
- backup retention, RPO/RTO, retention owner, and restore-test schedule; and
- named AWS, database, incident, privacy and deployment owners.

No value should point to the retired testing account.

## 3. Secure the fresh AWS account in the Console

The client creates the new AWS account and controls its root email, payment
method, recovery options and MFA from the outset. These are not transferred from
the project team. The client root owner performs the root-only steps in this
section; routine client operators receive named, delegated access.

1. Open **Account > Account settings**. Confirm the root email, legal/contact
   details and payment method are controlled by the client.
2. Open **Account > Alternate contacts**. Set billing, operations and security
   contacts to maintained organisational mailboxes.
3. Open **IAM > Dashboard > Security recommendations** (or root security
   credentials). Register two independent root MFA methods. Confirm there are no
   root access keys; never create one.
4. Create at least two named human administrator identities using the client's
   approved federation method and require MFA. Do not create a shared deployment
   user or distribute long-lived access keys.
5. Decide whether IAM Identity Center/Organizations is appropriate for the
   account plan. Do not enable Organizations solely for this project while the
   client is intentionally remaining in a plan where that changes commercial
   terms. After the paid-plan transition, prefer group-based assignments and
   least-privilege permission sets.
6. Open **Billing and Cost Management > Budgets** and confirm the account can
   create budgets and deliver email notifications. CDK creates workload budget
   resources, but billing access/contact ownership remains an account setting.
7. Open **CloudTrail** and note any account/organisation trails already present.
   Do not create a duplicate manually; `WmOperations-<stage>` owns the project
   trail. After deployment, verify it is logging and the audit bucket receives
   digest-validated records.
8. Review **Service Quotas** for Lambda concurrency, SES, API Gateway, SQS and
   the providers used by the workload. Keep `workerMaxConcurrency` conservative
   until load tests and quotas justify an increase.

Root custody remains with the client root owner and must not be shared with the
project team or routine operators. The remaining steps use named, non-root
temporary sessions in the new client account.

## 4. Prepare the local workstation

Required tools are Git, PowerShell, Python 3.13, Node 22, npm, and AWS CLI v2.33
or later. CDK packages Python 3.14 Lambda runtimes, but repository tooling and CI
use Python 3.13.

```powershell
aws --version
python --version
node --version
npm --version
git status --short
```

Authenticate with short-lived credentials. `aws login` requires AWS CLI 2.32+
and automatically rotates a temporary local session; Express provisioning
requires 2.33+.

```powershell
aws login --profile wm-admin --region ap-southeast-2
$identity = aws sts get-caller-identity `
  --profile wm-admin --region ap-southeast-2 | ConvertFrom-Json
$identity
$expectedAccount = '<CLIENT_AWS_ACCOUNT_ID>'
if ($identity.Account -ne $expectedAccount) { throw 'Wrong AWS account.' }
if ($identity.Arn -match ':root$') { throw 'Do not operate as root.' }
```

Stop if the account or principal is wrong. In particular, do not continue if
the command resolves to the project testing account. Then install pinned
dependencies:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --requirement requirements.txt
npm ci
python -m pytest infra/tests tests -q
```

The virtual environment must remain active when running CDK because `cdk.json`
invokes `python infra/app.py`.

## 5. Create provider secrets in the Console

Create new restricted Google Maps and OpenAI keys in client-controlled provider
projects. Do not copy keys or secret values from the testing deployment.

In **Secrets Manager**, ensure the Console Region is **Asia Pacific (Sydney)**.
Create a distinct secret per environment for Google Maps and OpenAI:

1. Choose **Store a new secret > Other type of secret**.
2. Store either the raw key string or JSON with `api_key` or `key`.
3. Use a descriptive name such as `wm/dev/google-maps` or `wm/dev/openai`.
4. Keep the default AWS-owned encryption key unless the client has approved and
   designed a customer-managed KMS path.
5. Add project/environment/owner tags and record only the secret ARN.
6. Do not enable automatic rotation unless the provider integration and rotation
   Lambda have been designed and tested.

Restrict the Google server key to the exact required server-side APIs and its
approved project. Put the OpenAI key in a dedicated project with an approved
budget/limit. Verify metadata without printing values:

```powershell
aws secretsmanager describe-secret --secret-id '<GOOGLE_SECRET_ARN>' `
  --profile wm-admin --region ap-southeast-2
aws secretsmanager describe-secret --secret-id '<OPENAI_SECRET_ARN>' `
  --profile wm-admin --region ap-southeast-2
```

## 6. Configure SES in the Console

In **Amazon SES**, set the Region to **Asia Pacific (Sydney)**.

1. Open **Verified identities > Create identity** and verify the client-owned
   sending domain (preferred) or an initial sender address.
2. Publish the DKIM DNS records. Coordinate SPF and DMARC with the domain owner.
3. Choose a sender for `PASSWORD_RESET_FROM_EMAIL`; it also sends verification
   and export notifications.
4. Open **Account dashboard** and inspect sandbox/production access. A sandboxed
   account can normally send only to verified recipients. Request production
   access before public registration.
5. Configure maintained bounce/complaint monitoring and suppression handling.
   Confirm the operational owner receives relevant alerts.

Verify from the CLI:

```powershell
aws sesv2 get-account --profile wm-admin --region ap-southeast-2
aws sesv2 list-email-identities --profile wm-admin --region ap-southeast-2
```

## 7. Publish the CDK permissions boundary and bootstrap

Every CDK-created role receives the managed policy `WM-CdkBoundary`. Create it
before synthesis/deployment:

```powershell
$account = aws sts get-caller-identity --profile wm-admin `
  --query Account --output text
$boundaryArn = "arn:aws:iam::${account}:policy/WM-CdkBoundary"
aws iam get-policy --policy-arn $boundaryArn --profile wm-admin 2>$null
if ($LASTEXITCODE -eq 0) {
  aws iam create-policy-version --policy-arn $boundaryArn `
    --policy-document file://bootstrap/WM-CdkBoundary.json `
    --set-as-default --profile wm-admin
} else {
  aws iam create-policy --policy-name WM-CdkBoundary `
    --policy-document file://bootstrap/WM-CdkBoundary.json `
    --profile wm-admin
}
```

An IAM managed policy has at most five versions. If necessary, delete a reviewed
old non-default version first.

Bootstrap CDK once with termination protection and the boundary:

```powershell
npx cdk bootstrap "aws://${account}/ap-southeast-2" `
  --profile wm-admin `
  --termination-protection `
  --custom-permissions-boundary WM-CdkBoundary
```

In **CloudFormation**, verify `CDKToolkit` is `CREATE_COMPLETE` or
`UPDATE_COMPLETE`, termination protection is enabled, and the bootstrap roles
carry the boundary. Do not edit bootstrap resources manually.

## 8. Deploy GitHub OIDC identity

Check `cdk.json` contains the exact GitHub repository identifier expected by
`infra/stacks/identity_stack.py`, then review and deploy:

```powershell
npx cdk diff WmIdentity --profile wm-admin
npx cdk deploy WmIdentity --profile wm-admin --require-approval broadening
```

Record the CloudFormation outputs `GitHubDeployerDevRoleArn` and
`GitHubDeployerProdRoleArn`.

In **IAM > Identity providers**, verify the GitHub OIDC provider has URL
`https://token.actions.githubusercontent.com` and audience `sts.amazonaws.com`.
In **IAM > Roles**, inspect both deploy roles:

- trust is limited to the exact repository;
- dev trusts the `dev` GitHub environment;
- production trusts the `production` GitHub environment;
- the audience condition is `sts.amazonaws.com`; and
- the `WM-CdkBoundary` permissions boundary is attached.

There are no AWS access-key secrets in GitHub. If the client repository owner or
name changes, add and verify the new subject before removing the old trust.

## 9. Configure the shared API Gateway logging role

API Gateway has one account-level CloudWatch role per account and Region; CDK
deliberately does not own this shared setting.

1. In **IAM > Roles**, create or select a role trusted by
   `apigateway.amazonaws.com`.
2. Attach AWS-managed policy
   `service-role/AmazonAPIGatewayPushToCloudWatchLogs`.
3. In **API Gateway**, switch to **Asia Pacific (Sydney)**, open
   **Settings > Logging > Edit**, and enter that role ARN.
4. Save and verify the displayed ARN.

CLI verification:

```powershell
aws apigateway get-account --profile wm-admin --region ap-southeast-2 `
  --query cloudwatchRoleArn --output text
```

## 10. Provision Aurora PostgreSQL Express

Create a new, empty cluster in the client account. There is no database,
snapshot, credential, or participant-data migration from the testing account.
If a future data migration is required, it needs a separately approved and
documented privacy, schema, verification and rollback plan.

The repository script is idempotent and enforces project settings. For dev:

```powershell
.\scripts\provision-aurora-express.ps1 -Stage dev -Profile wm-admin
```

For approved paid-plan production:

```powershell
.\scripts\provision-aurora-express.ps1 `
  -Stage prod -Profile wm-admin -AllowProduction -BackupRetentionDays 30
```

The script creates/reuses `wm-<stage>-aurora-postgres`, enables the Data API and
PostgreSQL CloudWatch log export, sets dev/prod deletion protection, configures
backup retention, creates a privacy-preserving cluster parameter group, and sets
database log retention to 14 days in dev or 90 in prod. It tags the external
resource and refuses root. Express clusters are Aurora Serverless, use an
AWS-owned encryption key, have AWS-managed Internet Access Gateway connectivity,
and are IAM-only. Do not make an instance publicly accessible.

For an existing cluster, attaching the logging parameter group can require a
maintenance reboot. Review pending modification and the maintenance window,
then explicitly use `-ApplyLoggingParameterGroup`; do not force an unplanned
production reboot.

In **RDS > Databases > wm-<stage>-aurora-postgres**, verify:

- status `Available`, engine Aurora PostgreSQL, and expected stage/owner tags;
- **Connectivity & security > RDS Data API** enabled;
- deletion protection off for dev and on for prod;
- backup retention 1 day for dev or approved production value;
- the live default Serverless v2 minimum/maximum ACU range is acceptable for the
  workload and current account plan;
- PostgreSQL log export enabled;
- the expected cluster parameter group and any `pending-reboot` state; and
- no public instance exposure.

In **CloudWatch > Log groups**, verify
`/aws/rds/cluster/wm-<stage>-aurora-postgres/postgresql` and its retention.
Record the cluster ARN from the script output; do not record a generated IAM
token because it expires after 15 minutes.

## 11. Deploy the data stack and initialize the database

Deploy `WmData-dev` first. All URLs must be HTTPS and have the required suffix,
but placeholders are acceptable until the API URL exists:

```powershell
npx cdk deploy WmData-dev --profile wm-admin --require-approval broadening `
  -c stage=dev `
  -c databaseClusterArn='<CLUSTER_ARN>' `
  -c workerMaxConcurrency=2 `
  -c monthlyBudgetUsd='<APPROVED_USD>' `
  -c budgetAlertEmail='<BUDGET_MAILBOX>' `
  -c operationalAlertEmail='<OPS_MAILBOX>' `
  -c googleMapsSecretArn='<GOOGLE_SECRET_ARN>' `
  -c openAiSecretArn='<OPENAI_SECRET_ARN>' `
  -c passwordResetFromEmail='<VERIFIED_SES_SENDER>' `
  -c passwordResetLinkBase='https://example.invalid/auth/password-reset/open' `
  -c emailVerificationLinkBase='https://example.invalid/auth/email-verification/open' `
  -c responseExportLinkBase='https://example.invalid/response-exports' `
  -c ttsProvider=disabled `
  -c wafMode=count
```

`WmData-<stage>` creates `wm-<stage>/database/application` with username
`wm_app` and a generated password. Initialize the database without printing the
password:

```powershell
$cluster = (aws rds describe-db-clusters `
  --db-cluster-identifier wm-dev-aurora-postgres `
  --profile wm-admin --region ap-southeast-2 | ConvertFrom-Json).DBClusters[0]
$outputs = (aws cloudformation describe-stacks --stack-name WmData-dev `
  --profile wm-admin --region ap-southeast-2 | ConvertFrom-Json).Stacks[0].Outputs
$secretArn = $outputs.Where({$_.OutputKey -eq 'DatabaseApplicationSecretArn'}).OutputValue
$secret = aws secretsmanager get-secret-value --secret-id $secretArn `
  --profile wm-admin --region ap-southeast-2 | ConvertFrom-Json
$env:WM_APP_PASSWORD = ($secret.SecretString | ConvertFrom-Json).password
$env:PGPASSWORD = aws rds generate-db-auth-token `
  --hostname $cluster.Endpoint --port $cluster.Port `
  --username $cluster.MasterUsername `
  --profile wm-admin --region ap-southeast-2
python scripts/initialize_aurora_express.py `
  --host $cluster.Endpoint --port $cluster.Port `
  --admin-user $cluster.MasterUsername
Remove-Item Env:WM_APP_PASSWORD, Env:PGPASSWORD
```

Apply the ordered migrations through the Data API:

```powershell
$env:DATABASE_RESOURCE_ARN = $cluster.DBClusterArn
$env:DATABASE_SECRET_ARN = $secretArn
$env:DATABASE_NAME = 'walking_meditation'
python scripts/apply_migrations.py --data-api `
  --profile wm-admin --region ap-southeast-2
Remove-Item Env:DATABASE_RESOURCE_ARN, Env:DATABASE_SECRET_ARN, Env:DATABASE_NAME
```

The result must include every pending migration through
`0010_privacy_policy_acceptance.sql`. Never edit or re-run an applied migration;
a checksum mismatch blocks the release.

## 12. Configure GitHub repository environments

In **GitHub > Repository settings**:

1. Protect `main`; require pull-request review and successful CI.
2. Create environments named exactly `dev` and `production`.
3. Require named reviewers for production and disallow administrator bypass
   where the organisation supports it.
4. Add these environment variables separately to both environments:

| Variable | Required value |
| --- | --- |
| `AWS_ACCOUNT_ID` | The 12-digit target account |
| `AWS_DEPLOY_ROLE_ARN` | Matching OIDC role output |
| `DATABASE_CLUSTER_ARN` | Matching Aurora cluster ARN |
| `API_RESERVED_CONCURRENCY` | Optional positive integer |
| `WORKER_MAX_CONCURRENCY` | Positive integer, initially conservative |
| `MONTHLY_BUDGET_USD` | Approved numeric budget |
| `BUDGET_ALERT_EMAIL` | Maintained billing mailbox |
| `OPERATIONAL_ALERT_EMAIL` | Maintained operations mailbox |
| `GOOGLE_MAPS_SECRET_ARN` | Environment-specific ARN |
| `OPENAI_SECRET_ARN` | Environment-specific ARN |
| `PASSWORD_RESET_FROM_EMAIL` | Verified SES sender |
| `PASSWORD_RESET_LINK_BASE` | HTTPS URL ending `/auth/password-reset/open` |
| `EMAIL_VERIFICATION_LINK_BASE` | HTTPS URL ending `/auth/email-verification/open` |
| `RESPONSE_EXPORT_LINK_BASE` | HTTPS URL ending `/response-exports` |
| `TTS_PROVIDER` | `disabled` or `polly` |
| `WAF_MODE` | `count` initially; production later `block` |
| `SMOKE_TEST_TTS_VOICE` | Optional `male` or `female`; must match smoke account's current study |

Add `SMOKE_TEST_EMAIL` and `SMOKE_TEST_PASSWORD` as environment **secrets**.
The smoke account must be synthetic, verified, enabled, dedicated to automation,
and not shared with a person. Do not store AWS credentials, provider keys,
database passwords, or JWT material in GitHub.

## 13. Deploy the workload

From protected `main`, open **Actions > Deploy > Run workflow**, choose `dev` or
`production`, and dispatch. The workflow obtains temporary OIDC credentials,
tests infrastructure, validates context, performs strict synthesis with
cdk-nag, shows a CDK diff, deploys the six workload stacks, resolves
`ApiBaseUrl`, and runs the post-deployment smoke suite.

For an operator-run equivalent, export the same variables used by
`.github/workflows/deploy.yml`, then run:

```powershell
python scripts/run_cdk_ci.py validate
python scripts/run_cdk_ci.py synth --strict
python scripts/run_cdk_ci.py diff `
  WmAlerting-dev WmData-dev WmGeneration-dev `
  WmExports-dev WmApi-dev WmOperations-dev
python scripts/run_cdk_ci.py deploy --require-approval never `
  --outputs-file cdk-outputs.json `
  WmAlerting-dev WmData-dev WmGeneration-dev `
  WmExports-dev WmApi-dev WmOperations-dev
```

Always review `cdk diff`; construct ID changes can replace resources. Stateful
resources and production stacks require special scrutiny. Never use hotswap or
CDK Express mode in production.

## 14. Complete the two-pass URL configuration

The first complete deployment creates `ApiBaseUrl`. Update the three GitHub
environment variables to exact generated URLs:

- `<ApiBaseUrl>auth/password-reset/open`;
- `<ApiBaseUrl>auth/email-verification/open`; and
- `<ApiBaseUrl>response-exports`.

`ApiBaseUrl` already includes the stage path and trailing slash. Redeploy from
the protected workflow and rerun smoke tests before enabling registration,
password reset, verification, or exports.

For Android App Links, configure the package name and release certificate
fingerprints in the API Lambda environment through the CDK-supported settings,
then verify `GET /.well-known/assetlinks.json`. Do not claim App Links readiness
while fingerprints are absent and the endpoint returns 404.

## 15. Console verification after deployment

Use the Console only to verify CDK-managed resources, not to edit them.

- **CloudFormation:** all expected stacks complete; production data stack has
  termination protection; no failed or unexplained drifted resources.
- **Lambda:** functions use expected names `wm-<stage>-...`, reserved concurrency
  matches the decision, and recent invocations have no persistent errors.
- **API Gateway:** `wm-<stage>-api`, deployed stage, execution/access logging,
  binary `audio/mpeg`, and account CloudWatch role are present.
- **SQS:** generation/export source queues have four-day retention, DLQs have
  14-day retention, redrive is five receives, and no backlog remains.
- **EventBridge Scheduler:** minute outbox recovery and daily maintenance
  schedules are enabled with scheduler DLQs.
- **Secrets Manager:** application database, JWT signing, rate-limit pepper,
  Google and OpenAI secrets exist; values have never entered logs or variables.
- **S3:** export and audit buckets block public access and require TLS; export
  lifecycle is seven days; dev-only generation archive is seven days; no
  production generation archive exists.
- **CloudWatch:** log groups have expected retention; alarms exist and SNS
  subscriptions are confirmed.
- **CloudTrail:** project trail is logging and audit delivery is current.
- **Budgets:** amount and mailbox match the approved decision.
- **SES:** sender is verified and production access/sending are enabled before
  public use.

Run the commands and manual acceptance flows in `testing-guide.md` and record
the release commit, outputs, migration list, smoke result, alarms, and completion
time.

## 16. Production-only controls

Production requires the paid-plan decision, `prod` Aurora provisioned with
`-AllowProduction`, approved backup retention (normally 30 days), deletion
protection, protected GitHub production approval, and every launch gate in the
operations handbook.

Deploy WAF initially with `WAF_MODE=count`. Exercise authentication, 16 KiB
export login, questionnaire payloads, route/script payloads, and TTS requests
using synthetic data. Review the redacted `aws-waf-logs-wm-prod-api` log and
metrics. Tune only narrow rules through CDK, change to `block`, review the diff,
redeploy, and repeat smoke/acceptance tests. Never disable the entire ACL to fix
a false positive.

Perform and record a point-in-time restore into an isolated cluster, apply
schema checks, run application/database smoke tests, measure RPO/RTO, and clean
up only after evidence is retained. A snapshot or configured retention period
without a successful restore test is not recovery evidence.

## 17. Client acceptance and session closure

The client deployment is accepted from resources created in the new client
account; nothing in the testing account is transferred or treated as the live
baseline. Record the client repository commit, environment reviewers, delegated
AWS roles, SES operating procedure, client-owned Google/OpenAI project access,
alert mailboxes, backup/retention decisions, and break-glass procedure. Produce
the non-secret inventory, stack states, API URL, cluster ID, OIDC role ARNs,
budget/alarms, restore evidence and known gaps from the client account after
deployment.

The client operator must demonstrate a non-root temporary login, inspect the
deployed state, approve a protected deployment, complete the synthetic smoke
suite, and receive a test alert. If the project team received temporary delegated
access to assist the build, remove that access after client acceptance and record
the change. No access to the old testing account is required.

End the local AWS session:

```powershell
aws logout --profile wm-admin
```
